## 一 先理解六个核心概念

### 预占与落单

预占是先在 Redis 中占一个名额，并留下用户和订单身份。落单是消费者在 MySQL 中真正写订单、扣数据库库存。二者之间允许短暂不同步，因此接口拿到订单 ID 只能说明已受理，需要查询最终结果。

可以把 Redis 看成“名额预占账”，MySQL 看成“已创建订单账”。这只是理解两类状态的比喻：Redis 预占账在当前设计中也是重要业务状态，不能随意清空。

### 锁与幂等

锁解决多个执行者同时修改同一业务的问题；幂等解决同一个任务被重复执行的问题。消息可以先后重复到达，即使每次都成功拿到锁，也需要查重或唯一约束防止第二次扣库存。

当前订单用 Redisson 用户锁与查重，本地又补了业务唯一索引；真实数据库是否有该约束仍待核实。不能用“我加了锁”替代幂等设计。

### Confirm 与 Return 与消费 ACK

Confirm 是生产者等待 broker 的接收结果；Return 用来识别 mandatory 消息无法路由的情况；消费 ACK 是消费者告知 broker 本次投递可以确认。它们分属不同环节，不代表同一个业务完成信号。[RabbitMQ 确认机制](https://www.rabbitmq.com/docs/confirms)

项目把成功落单放在数据库事务里，把消费 ACK 放在业务方法成功返回后。新加的重复键捕获属于另一条路径：数据库回滚后仍按成功返回，需要核查冲突身份，不能一概当成原订单成功。

### 重试与重复消息

重试意味着再尝试一次，结果可能是第一次本来就成功了，只是响应没回来。因此重试和幂等要一起设计。消息系统无法仅靠发送端超时判断数据库是否已经落单。

项目保持原 orderId 重投，发送关联 ID 每次不同。前者表达同一笔业务，后者区分不同投递尝试。

### 死信与归档

死信队列是失败消息的隔离路径；归档是在数据库保存原始消息供后续核查。两者都不表示故障已修复。业务队列必须关联死信交换机，拒绝消息才能沿预期路径流转。当前代码只声明 DLX、DLQ 和它们之间的绑定，业务队列关联仍待核实。[死信配置依据](https://www.rabbitmq.com/docs/dlx)

### 补偿与取消围栏

补偿是纠正已经发生的预占等动作，必须核对原订单身份。取消围栏是在数据库先记下“这笔原订单不许再创建”的决定，让延迟到达的旧消息无法落单，然后再释放 Redis 预占。

它不是把 Redis、MQ、MySQL 一起回滚，而是让可持久化的状态和可重试操作逐步收敛。本地有这一原型，但全链路恢复仍待验证。

## 二 项目介绍参考稿

### 一分钟介绍

我做的是基于黑马点评课程的本地生活后端实践，包含验证码登录、商铺查询、点赞关注、签到、附近商铺和优惠券秒杀。前期跟随课程完成，后续在 AI 辅助下将订单异步处理从 Redis Stream 改为 RabbitMQ，重点学习消息确认、重试和失败治理。

普通业务中，我实践了 Redis 登录态、空值缓存、集合关系与滚动 Feed。秒杀链路用 Lua 完成库存与重复购买判断并预占，当前把待发订单写进 Redis ZSet，由后台 Relay 先发送到 RabbitMQ，收到 Confirm ACK 且检查没有 Return 后删除待发记录；消费端通过 Redisson、数据库事务和幂等检查落单。

接口返回订单 ID 表示已受理，最终结果通过状态查询确认。目前有失败归档和取消补偿原型，也明确保留 DLX 关联、真实库索引与故障恢复待验证项，没有虚构吞吐或延迟数据。

### 三分钟展开

业务上有两条线。一条是普通读写与互动：登录需要共享身份状态，商铺读取需要减少重复回源，点赞关注需要成员判断和关系运算，Feed 需要稳定地向后翻页。我使用 Redis 的 Hash、String、Set、ZSet、Bitmap 和 GEO 对应这些需求。商铺当前入口启用空值缓存；互斥和逻辑过期是已封装的候选策略，没有包装成正在启用。

另一条是秒杀，先区分库存与一人一单。库存依赖数据库 stock>0 条件扣减；重复购买需要用户维度互斥和幂等。课程路线从 JVM 锁过渡到共享 Redis 锁，再使用 Redisson 降低锁协议维护成本。之后将资格预检查放进 Lua，把请求受理与数据库落单解耦。

历史 Stream 方案用消费组、Pending 和 ACK 处理异步任务，但实现还存在恢复与失败治理缺口。RabbitMQ 改造主要是学习专用 MQ 的确认和消费控制，不是证明 Stream 性能不够。引入 MQ 后又产生预占完成但尚未发送的窗口，所以当前 Lua 同时写 Redis outbox，由 Relay 在确认且没有 Return 时删除待发项。

消费端允许消息重复，通过查重、锁和数据库事务处理。当前本地补了业务联合唯一索引，真实库是否应用还需要验证。多次失败按“有限重试、归档、核查后重投或取消”处理。取消时先提交数据库围栏，再按预占订单号释放 Redis，防止旧消息又创建订单。

我不会把这些代码直接说成生产级可靠性结论。本轮 14 项局部测试通过，但不包括真实 RabbitMQ、MySQL、Redis 的故障闭环，性能也没有可引用的报告。下一步优先补齐提交完整性、死信关联和真实环境对账验证。

## 四 技术亮点怎样讲才经得起追问

| 亮点 | 先讲业务问题 | 再讲关键机制 | 主动交代的边界 |
| --- | --- | --- | --- |
| 缓存策略 | 不存在 ID 与热点过期是两类问题 | 空值缓存、互斥重建、逻辑过期 | 当前只启用空值策略，其他封装待切换验证 |
| 多层秒杀约束 | 库存与用户重复购买要分别限制 | Lua 预占、用户锁、DB 条件扣减、查重 | 本地唯一索引未证明已在真实库生效 |
| 异步投递责任 | 预占后进程退出可能未发 MQ | Redis 同脚本 outbox、确认后删除 | Redis 数据安全仍是前提；允许重复投递 |
| 消费与事务边界 | DB 成功而 ACK 丢失会重投 | 业务幂等、代理事务、手动 ACK | 新重复键分支需核对冲突身份 |
| 失败恢复原型 | 不能无限重试，也不能盲目返库存 | 归档、原身份重投、取消围栏、补偿标记 | 未提交依赖、DLX 和全链路验证仍待完成 |

回答结构统一为：业务约束 → 旧方案哪里失效 → 为什么选这个机制 → 代码落在哪 → 能证明什么 → 仍有什么风险。性能数字不是讲清技术取舍的必要条件。

## 五 高频问题与参考回答

### 业务与 Redis

**1 你项目是微服务吗，Redis 扮演什么角色**

是 Spring Boot 单体后端，外接 MySQL、Redis 和 RabbitMQ。Redis 除缓存外，还承载登录态、签到、预占与待发消息等状态。不能把所有 Redis key 都当成可随意淘汰的缓存，也没有微服务拆分与集群高可用的实现证据。

**2 Token 为什么放 Redis，为什么不直接 JWT**

这里 Token 是随机 UUID，Redis Hash 保存登录上下文，便于统一失效与滑动续期。JWT 可以减少某些查存储开销，但撤销和续期策略不同。项目没有 JWT，实现的是中心化共享会话，不能混讲。

**3 两个拦截器为什么分开，ThreadLocal 什么时候清理**

刷新拦截器先解析可能存在的 Token，给公开接口也补充当前用户信息；登录拦截器再对受保护路径检查身份。请求完成后 remove，避免线程池复用导致串用户。消费者从消息读取 userId，不依赖请求 ThreadLocal。

**4 缓存穿透、击穿、雪崩怎么区分**

穿透是不存在的数据持续回源；击穿是某个热点失效引发集中回源；雪崩是大量缓存同时失效或 Redis 故障引发整体压力。项目启用空值缓存，封装了击穿策略；TTL 抖动、限流熔断等属于可讨论的改进，不能说已落地。

**5 为什么空值 TTL 比普通数据短，是否用了布隆过滤器**

短 TTL 限制无效 ID 的重复回源，又减少数据随后创建时被旧空值遮挡的时间。当前两分钟空值、三十分钟正常数据。没有布隆过滤器，不能把它写成现有技术点；随机大量无效 ID 仍需其他防护。

**6 互斥重建与逻辑过期怎么选**

互斥重建让未拿锁请求等待，偏向获得新值；逻辑过期保留旧值并异步重建，偏向可用性，需要业务接受短暂旧数据。当前实现逻辑过期 miss 直接 null，需要预热与缓存格式迁移，不能只取消注释就认定切换完整。

**7 先更新数据库再删缓存能强一致吗**

不能。删除可能失败，并发读也可能把先前读到的旧值回填。项目采用这个基本顺序，但没有删除重试或可靠通知闭环。可提出可靠失效通知、版本控制或对账作为改进，并说明尚未实现。

**8 点赞为什么用 ZSet，能保证计数正确吗**

用户作为 member 去重，时间 score 支持展示顺序。当前 range(0,4) 展示最早点赞的五人。ZSet 去重不能让 DB 计数与 Redis 双写自动原子化，同用户并发“先判断再更新”仍可能重复加计数。

**9 Feed 为什么用滚动分页，offset 解决什么**

按最大时间戳继续向旧数据读取，减少新动态插入导致页码偏移；同一毫秒可能有多条，需要 offset 跳过已读的同分值记录。当前代码还在新页最小时间与上页边界相同时累加 offset。Feed 写入是同步逐粉丝推送，存在大用户写放大。

**10 Bitmap 和 GEO 有什么边界**

Bitmap 适合按日表达是否签到；31 天的有效位不超过 31 位，但总内存还有 key 与对象开销。GEO 用于圈定附近候选，再回 DB 取详情；当前未显式距离升序，也缺商铺更新后的 GEO 同步。不能夸成已验证的最近优先推荐系统。

### 秒杀与分布式锁

**11 防超卖为什么不只在 Java 判断 stock 大于零**

多个线程可同时读到旧库存。将条件和扣减合并成一条数据库 UPDATE，并根据影响行数判断，才没有外部先读与更新间的竞争窗口。项目是 stock>0 条件扣减，没有版本号字段。

**12 防超卖就能一人一单吗**

不能。库存足够时，同一用户多次请求仍可能都扣成功。一人一单是用户与券的联合约束，需要查重、互斥和最终数据库唯一性。锁与条件扣库存分别承担不同职责。

**13 synchronized 为什么不够，能不能直接锁整个方法**

单 JVM 监视器不能约束其他 JVM；锁整个业务还可能让不同用户互相阻塞。项目从用户粒度 JVM 锁演进到共享 Redis 用户锁；当前仍按用户串行化不同券，粒度可进一步评估，但不是已做的优化。

**14 SETNX 后再 EXPIRE 有什么问题**

两条命令之间退出会留下无过期锁。当前使用带 TTL 的 setIfAbsent，一次完成 NX 与租约设置。还要判断是否真正获得锁，仅持有者才尝试释放。

**15 为什么 GET 比较后再 DEL 还不安全**

即使比较时是自己的锁，在 DEL 前也可能过期并由其他线程接手。Lua 把归属比较与删除合并，消除这个插入窗口。它只解决安全释放，不会阻止过期旧持有者继续执行业务。

**16 UUID 加线程 ID 能解决锁自动过期吗**

不能。它区分持有者，不延长租约。固定 TTL 到期后旧线程仍可能运行；需要续期或其他互斥设计，并用数据库约束防止产生非法结果。

**17 Redisson 看门狗为什么有用，能保证绝对安全吗**

未显式指定 leaseTime 时，库可安排续期，降低正常长业务超过固定租约的风险；指定租约则按相应租约路径处理。项目版本默认 watchdog 超时 30 秒，按租约的三分之一调度续期，默认约 10 秒；这是库默认机制，不是项目故障实测。长暂停、网络分区或故障切换仍可能突破锁的假设。当前是无参数 tryLock，没有使用 RedLock 或 fencing token。[3.16.3 Lock](https://github.com/redisson/redisson/blob/redisson-3.16.3/redisson/src/main/java/org/redisson/RedissonLock.java)、[默认配置](https://github.com/redisson/redisson/blob/redisson-3.16.3/redisson/src/main/java/org/redisson/config/Config.java)、[续期调度](https://github.com/redisson/redisson/blob/redisson-3.16.3/redisson/src/main/java/org/redisson/RedissonBaseLock.java)

**18 可重入是不是同一个用户都能重复获得锁**

不是。重入身份与 Redisson 实例和持有线程有关，同一个线程重复进入可增加持有计数；另一个线程即使 userId 相同仍需竞争。重入不是业务重复购买许可。

**19 加锁范围为什么要包含事务提交**

若先释放锁、再提交事务，后继线程可能在前一事务提交前查不到订单。当前外层拿锁，调用 self 的事务方法，代理完成提交后返回，再 finally 解锁。单纯在同一对象内直接调用带注解方法，默认代理模式下不会因此新触发事务拦截。[Spring 代理事务](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)

**20 多线程为什么会导致事务问题，消费者怎么处理**

请求线程事务不会自动传给消费者；消费者仍可通过代理调用事务方法开启自己的事务。项目注入 self，避免历史中请求先初始化 proxy、消费者随后才可用的依赖。不能简单背“多线程事务必然失效”。

### Lua 与 Redis Stream

**21 Lua 为什么能防止预占竞争，可以直接替代事务吗**

正常执行期间其他客户端命令不会插入库存判断、用户判断与预占写入之间。但它只涉及本 Redis 执行范围；不包含数据库提交和 MQ，也不提供 SQL 式的错误自动回滚。要让脚本短小、在写入前尽量校验参数与类型。

**22 为什么先 Redis 扣库存，再 MySQL 扣一次，不是扣了两份吗**

这是两份用途不同的库存状态：Redis 控制受理名额，MySQL 记录已落单的库存。正常最终各自从同一初始数减去成功订单数，不是在同一账本扣两次。中间失败需要核查后释放 Redis 对应预占。

**23 活动时间、预热和 Redis key 怎么保证正确**

当前 Lua 只判断库存 key、库存数和购买记录，没有活动时间校验，不能说 key 存在就代表活动正在进行。建券时会写 Redis 库存，但 DB 与 Redis 不在同一事务里。活动窗口、预热失败与重复初始化属于待完善和验证内容。

**24 BlockingQueue、Stream 和 RabbitMQ 怎么比较**

BlockingQueue 在进程内，重启恢复薄弱；Stream 提供外部记录与消费组，任务可与 Redis 预占一起写入；RabbitMQ 提供另一套专用消息基础设施，但新增跨系统发送责任和维护成本。项目选择 RabbitMQ 是学习改造，没有性能优劣实测。

**25 Stream 的 Pending 是什么，读 0 会恢复所有消费者吗**

PEL 表示已交付但未 ACK 的消息。历史代码读 ID 0 处理的是指定消费者自己的 Pending，不自动覆盖其他消费者；接管需另行设计。XACK 移除待确认记录，不直接删除消息正文。当前 Stream 是历史方案，不能指着现有 ZSet 说它就是 Stream。

### RabbitMQ 与最终结果

**26 为什么 Lua 之后不能直接发 MQ 就结束**

预占后、发送前进程可能退出。当前用 Lua 同时写待发记录，使发送责任留下来，Relay 后续处理。这弥补应用进程退出窗口，但 Redis 丢数据仍可能丢掉恢复依据。

**27 outbox 为什么用 ZSet，为什么不是完整分布式事务**

member 保存固定业务身份，score 保存下次发送时间，适合扫描到期任务。Lua 只把预占与待发记录放在 Redis 内，MQ 仍是后续独立发送，因此不是跨 Redis、MQ、MySQL 的原子事务，也不是 MySQL 订单与消息同事务的数据库 Outbox。

**28 Relay 为什么先把时间推迟，为什么确认后再删**

推迟让未确认项保留并稍后再尝试；先删除再发送会暴露退出丢任务窗口。确认后删除仍有“发送已成功但删除前退出”的重复窗口，所以消费幂等必不可少。读取与推迟不是原子认领，多实例还可能重复抓取。

**29 Confirm ACK 后为什么还检查 Return**

不可路由不必表现为 Confirm NACK。当前 Relay 同时看本次确认与退回结果，避免只依据 ACK 删除待发记录。即使两项检查都通过，也只是发送环节结果，不是数据库订单已创建。

**30 Confirm 超时为什么不立刻返库存**

超时只说明没及时得到结果，消息可能已经被接收甚至消费。立即返库存会与原消息继续创建冲突。当前保留待发项重投，失败取消则先核查订单和预占、建立取消围栏。

**31 最多重试三次是什么意思，是四次调用吗**

maxAttempts(3) 含首次，最多三次业务调用，追加重试两次。固定间隔一秒，是监听器线程内重试，没有配置成一秒后重新入队的延迟消息。反序列化等方法调用前错误需要另查容器策略。

**32 basicNack 的 false、false 各是什么，prefetch=1 又是什么**

第一个 false 是不批量拒绝多个 deliveryTag，第二个 false 是不重新进入原队列。是否进入 DLQ 依赖业务队列的 DLX 配置。prefetch=1 限制每个消费者未确认投递数量，不是总系统只能消费一条，也不是全局限流。

**33 消费 ACK 丢失会怎样，能否做到恰好一次**

数据库可能已提交，broker 没收到 ACK 时会重投。业务需要让重投查到已有结果，避免重复扣库存。当前目标是允许重复投递、幂等业务效果和可核查恢复，没有端到端恰好一次或零丢单证明。

**34 数据库唯一索引不是已经补了吗，为什么仍列风险**

HEAD 没有，本地 SQL 与初始化器新增了补索引逻辑。真实库可能未执行、已有重复数据、存在同名错误定义，初始化器也不是完整迁移工具。应读实际 schema 验证。当前广泛捕获 DuplicateKeyException 也未核对冲突订单，不能一概认定原 ID 成功。

**35 不用分布式锁，只靠唯一索引可以吗**

正确的业务唯一约束和数据库事务可以作为最终约束，必须正确处理唯一冲突与回滚。锁可减少并发冲突、让查重路径更可控，但有依赖成本。项目保留 Redisson，不能直接宣称去锁后性能更好或代码已验证等价。

**36 死信落库后为什么还需要人工核查**

归档只保留失败事实。业务原因可能是数据库短暂异常、库存账差异、非法消息或身份冲突，处置不同。先查原订单是否创建、是否存在同用户同券其他订单、预占身份是否匹配，再决定重投或取消；不能对所有死信统一补库存。

**37 重投为什么不能生成新订单 ID**

新 ID 会让旧消息与新消息成为两笔身份不同的业务，增加状态查询、补偿与幂等冲突。当前重投沿用原 orderId、userId、voucherId，不重复执行预占扣减；不同发送尝试只换 CorrelationData。

**38 为什么不能只 INCR 库存再 SREM 用户**

重复执行会多返库存；旧订单还可能释放后来新订单的购买资格。当前取消 Lua 校验用户预占对应的原 orderId，并使用按订单的补偿标记。没有历史预占身份的消息不能自动猜测补偿。

**39 CANCEL_PENDING 为什么重要，Redis 失败怎么办**

它表示取消决定已在数据库提交，旧消息不得再创建，但 Redis 释放还没完成。Redis 失败后保留这个状态，后台任务继续；Lua 已成功而 SQL 更新失败则用补偿标记避免重复返还。API 目前把它也显示为 CANCELLED，要解释“取消决定生效”与“补偿完成”的区别。

**40 你如何证明这套链路可靠，做了哪些压测**

本轮 14 项局部测试通过，覆盖模拟业务与 H2 补偿分支；有旧的真实 Redis 脚本测试报告。没有当前完整 MQ 故障恢复与系统压测证据。后续要测试预占后退出、确认不确定、DB 提交后 ACK 丢失、取消与创建并发，并核对最终订单和库存账，不能用局部单测数量代替这些实验。

**41 发号器是什么，能证明支持多少并发**

时间差左移 32 位再拼接 Redis 日 INCR 序列，不是 Snowflake。需要考虑时钟、序列 key 被重置、数据丢失和边界容量。多线程生成示例没有秒杀完整链路，也没有提供系统可承受并发的结论；订单 ID 返回字符串以避免前端数值精度损失。

**42 项目还有哪些值得主动承认的问题**

优先说与主线直接相关的：缺失提交依赖、DLX 未核实、真实库唯一约束与重复键核查、活动窗口、恢复闭环。普通业务还有类型缓存类型冲突、点赞双写、Feed 同步写放大、GEO 更新与排序等。每个问题配具体检查或改进方法，避免把风险列表当成自己已经解决的成果。

## 六 模拟面试

建议先遮住参考回答，按顺序口述。以下是模拟脚本与评分依据，不是对本人已经完成面试的评分记录。每题应先给结论，再讲项目证据和边界。

### 第一轮 项目整体

**面试官：用一分钟介绍项目，讲清你自己做的部分。**

参考回答：课程实践完成普通业务与原秒杀路线；RabbitMQ 改造由 AI 辅助，目标是消息治理实践。先列业务，再讲 Lua 预占、ZSet 待发、MQ 消费落库，说明返回 ID 是已受理及当前验证边界。

追问：你能不看生成代码讲清哪三个关键窗口。

合格要点：预占后未发送、发送成功但确认或删除失败、数据库提交后 ACK 丢失。若目前不能讲清，就直接说明正在补齐，不说“全链路可靠”。

### 第二轮 缓存入口

**面试官：你说实现了逻辑过期，现在详情查询真的走它吗。**

参考回答：没有。当前 queryById 调 PassThrough，另外两种调用被注释。策略在 CacheClient 中封装，逻辑过期需要预热、不同 JSON 格式与旧值容忍，切换时应清理或迁移旧缓存。

追问：逻辑过期 key 不存在会发生什么。

合格要点：当前实现直接返回 null，不自动回源；不能只背“永不过期就解决击穿”。

### 第三轮 库存与重复购买

**面试官：只用 stock>0，为什么同一个用户还能买两份。**

参考回答：它约束库存，不表达用户购买次数。查重需要和创建一起处理；当前用户锁降低并发查重竞争，本地联合唯一索引提供数据库兜底方向，真实库需验证。

追问：索引冲突发生在扣库存之后，库存怎么办。

合格要点：扣库存与插订单同事务，异常穿出代理后回滚扣减；当前外层捕获重复键后 ACK，还需核对冲突是否确为同一业务结果。

### 第四轮 手写锁

**面试官：线程 A 锁过期，B 拿到锁，A 又来解锁，怎么处理。**

参考回答：owner 为 JVM UUID 与线程标识，Lua 比较归属再删除，A 不会删除 B 的锁。

追问：那么 A 继续写库，B 也写库，问题解决了吗。

合格要点：没有，安全释放不等于旧持有者失效；需要约束写入结果、租约维护及适当的 fencing 等设计，当前未实现 fencing。

### 第五轮 Redisson 与事务

**面试官：换 Redisson 后为什么还要数据库约束。**

参考回答：库减少锁协议维护工作，但不能消除全部暂停和故障；约束是最终数据规则。当前无参数 tryLock 失败抛异常，代理事务执行完后解锁。

追问：为什么不是在有注解的方法内部直接 this 调用。

合格要点：默认代理模式下自调用不触发新的事务拦截；消费者需要在自身线程经代理开启事务，不继承请求线程事务。

### 第六轮 Lua 范围

**面试官：Lua 原子了，为什么还会出现 Redis 有预占但 MySQL 无订单。**

参考回答：Lua 只完成 Redis 预占和待发记录。数据库由消费者稍后执行，这个暂态是异步设计允许的。失败后要继续投递、归档核查或取消。

追问：脚本写到一半运行时报错，会自动回滚吗。

合格要点：不能当成 SQL 回滚；类型和参数应提前检查，数据异常仍需要实验和核查。也要指出当前活动时间没进入脚本。

### 第七轮 技术选型

**面试官：Stream 已支持 ACK，换 RabbitMQ 是不是堆技术。**

参考回答：不是必须替换。Stream 可以继续完善；这次主要学习专用 MQ 的发送确认、重试与失败治理，没有证明性能更好。代价是多一套服务和预占到 MQ 的跨系统窗口。

追问：如果只需当前规模、追求简单，你会怎么选。

合格要点：基于实际运维与治理要求选择；没有业务必要时可以保留 Stream 并补恢复能力，不能靠“MQ 更高级”证明合理性。

### 第八轮 outbox

**面试官：Lua 成功后立刻杀应用，你的订单怎么办。**

参考回答：同一脚本已经写 ZSet 待发记录，Relay 恢复后继续发；前提是 Redis 数据保留。不是在 catch 里补发，因为进程退出可能根本走不到 catch。

追问：发送成功后、ZREM 前退出呢。

合格要点：会重复，保持原订单 ID，消费端幂等；两个 Relay 同时取也可能重复，目前未做原子 claim。

### 第九轮 三种确认

**面试官：Confirm ACK、Return、消费 ACK 分别说明什么。**

参考回答：区分发送接收、路由退回与消费确认三个环节。当前 Relay 等发送确认并检查无 Return 才删 outbox；消费端业务完成后才确认。

追问：有 Confirm ACK 就能告诉用户下单成功吗。

合格要点：不能；最终查 MySQL 订单，预占成功先回已受理。注意当前状态查询还有 NOT_READY 歧义。

### 第十轮 消费失败

**面试官：数据库一直报错，会重试多久，最后去了哪里。**

参考回答：本地总尝试三次，间隔一秒，耗尽后 NACK 且不回原队列。预期进入配置好的 DLX/DLQ，但当前业务队列关联没有证据，不能保证消息确实能进死信归档。

追问：已经建了 DLQ，为什么还不够。

合格要点：DLQ 与 DLX 的绑定只描述后半段；还需业务队列关联 DLX。随后归档也是保留问题，不是解决预占账差异。

### 第十一轮 补偿与迟到消息

**面试官：运营决定取消，旧消息刚好到消费者，库存怎么不乱。**

参考回答：创建与取消锁同一恢复行，取消先提交 CANCEL_PENDING 围栏则消费者不再落单；创建先提交则取消拒绝释放。之后 Lua 按原预占 orderId 释放，补偿标记阻止二次返还。

追问：Redis 已返还而数据库终态没写成功呢。

合格要点：SQL 保留 CANCEL_PENDING，重试脚本识别已补偿，再写终态；依赖 Redis 标记保留，真实故障闭环还没验证。

### 第十二轮 验证与诚信

**面试官：给我一个你测出来的吞吐数据，再说一个你独立处理的线上事故。**

参考回答：没有这样的项目证据，不能提供。能给出本轮 14 项局部测试及具体覆盖范围，RabbitMQ 是 AI 辅助改造，没有虚构线上经历。可进一步说明准备如何设计故障注入与对账验证。

追问：那你这个项目的价值是什么。

合格要点：业务建模、理解并发约束、划清确认与事务边界、识别恢复缺口、设计可检验实验；价值不能只依赖漂亮数字，也不能用概念背诵代替代码理解。

## 七 自测评分与练习顺序

每轮参考 0 到 3 分：0 分是核心概念错误；1 分是会说术语但无法定位项目；2 分是能解释代码路径；3 分是在此基础上讲清故障边界与验证方式。十二轮满分 36 分，只用于自测，不代表真实面试结果。

以下是必须纠正的错误，不用总分掩盖：把返回 ID 当最终落单、把 Confirm 当消费成功、把 Lua 当跨系统回滚、把 Lua 解锁当旧线程停写、把 NACK 不回队当必然进 DLQ、把幂等目标当已经验证零丢失。

练习按依赖顺序进行：

1. 手画普通业务与秒杀架构，找到真实入口；先能分清当前方案、历史方案与未启用封装。
2. 口述库存与用户重复约束，再解释手写锁、Redisson 与数据库事务；最后讲锁失效为什么还要数据约束。
3. 逐行阅读 seckill.lua 和 Relay，推演预占后退出、确认不确定、删除前退出三个窗口。
4. 阅读消费者与归档，解释三次总尝试、ACK 时机、DLX 缺口和序列化前置失败。
5. 阅读恢复服务，推演创建先发生与取消先发生，以及 Redis/SQL 各自失败；用原订单身份解释为何不能盲返库存。
6. 按证据清单做隔离环境实验，再将真实记录补进材料；没有做过的仍保留待验证状态。

当前最值得先练的一题是：“Lua 已预占，RabbitMQ 实际收到，但 Confirm 超时了。为什么不能立刻返库存，你准备怎样追踪这笔订单直到终态。”
